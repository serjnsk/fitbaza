# 05 — Открытые вопросы

Решения, которые нужно принять до старта или на ранних этапах разработки. Каждый вопрос имеет ID (OQ-N); при принятии решения фиксируем ответ прямо здесь и переносим следствия в требования.

## OQ-1. Название продукта

> ✅ **Решено (август 2026).** На период разработки — тестовое название **«fitbaza»**. Финальное рабочее название, домен и имена в App Store / Google Play утверждаются перед запуском — отдельная задача пре-лонч-чеклиста.

## OQ-2. Десктоп тренера в MVP

> ✅ **Решено (август 2026): Вариант A.** Веб-версия конструктора для тренера входит в MVP — это критически важно: работа тренера по составлению программ почти всегда идёт с компьютера. Мобильные приложения — для всех ролей, телефон тренер использует в зале.

<details><summary>Исходные варианты</summary>

- **Вариант A (принят):** мобильные приложения для всех + веб-версия конструктора для тренера. Тренеры массово пишут программы с компьютера (так работает TRNR), а телефон используют в зале.
- **Вариант B (отклонён):** только мобильные приложения, десктоп — этап 2. Быстрее выйти, но рискуем проиграть конструктору TRNR в самом частом сценарии.

</details>

## OQ-3. Технологический стек

> ✅ **Решено (август 2026).** Принят стек: React Native + Expo (мобильные), React + Vite (веб-конструктор и админка), TypeScript-монорепо; оффлайн — PowerSync (self-hosted) + SQLite ↔ PostgreSQL; backend — Node.js/NestJS + Redis + S3-совместимое хранилище; хостинг в РФ. Полное обоснование, альтернативы и обязательные спайки — в [06 — Технологический стек](06-tech-stack.md). Финальная валидация — с нанятым разработчиком.

## OQ-6. Хранение и обработка видео

> ✅ **Решено (август 2026): своё хранилище — подтверждено.** Публичных удобных альтернатив нет: YouTube в РФ частично заблокирован (нужен VPN), Rutube — реклама и неудобный плеер. Остаток вопроса переносится в этап 2: расчёт стоимости хранения/трафика на одного тренера и лимиты в тарифах (связано с OQ-8).

## OQ-9. Стартовая база упражнений

> 🔶 **Частично решено (август 2026): требования уточнены, источник контента — открыт.**
>
> Зафиксировано:
> - Нужна база упражнений по **тренажёрному залу и кроссфиту** (EX-1).
> - Тренер привязывает к упражнениям базы **свои видео, которые видит только он** (и его клиенты в назначенных тренировках) — другим тренерам чужие видео недоступны (EX-2).
> - **Публичные видео для всех упражнений НЕ обязательны** — найти такой контент нереально, стартовая база может быть без видео.
>
> Остаётся решить — откуда контент самой базы (названия, описания, группы мышц, оборудование):
> - **Предложение:** собственная стартовая база ~300–500 движений (RU/EN названия для поиска), описания сгенерировать (частичный ранний запуск AI-1) и вычитать; фото/схемы опционально. Открытые англоязычные базы (wger, free-exercise-db) использовать как референс структуры и полноты списка, а не как готовый контент.
> - Следующий шаг: составить черновик списка движений по категориям (зал: жимы/тяги/присед/изоляция…; кроссфит: гимнастика/ТА/кардио…).

## OQ-10. Распознавание текста тренировок

> ✅ **Принцип зафиксирован (август 2026).** Программа хранится **не текстом, а структурой** — набором упражнений с показателями (канонический формат данных). Но удобство создания должно быть таким же простым, как ввод текста. Значит, текстовый ввод — это **интерфейс поверх структуры**:
>
> 1. Тренер печатает как в заметках («Присед 5х5 70%», «EMOM 12…»).
> 2. Парсер на лету распознаёт упражнения, подходы, проценты, форматы таймера и показывает распознанную структуру рядом с вводом.
> 3. Распознанные упражнения линкуются к базе (EX-1); нераспознанные строки остаются текстовыми и конвертируются в структуру одним действием.
>
> Реализация: спайк №4 в [06 — Технологический стек](06-tech-stack.md) (правила/грамматика, без LLM в MVP). UX «текст ↔ структура» — ключевая задача дизайнера в конструкторе.
